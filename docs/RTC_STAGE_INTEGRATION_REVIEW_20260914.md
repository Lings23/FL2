# RTC阶段顺序与逐步集成评估

日期：2026-09-14。结论：原计划的机制研究顺序基本合理，版本继承和集成时机需要修正。
用户指出R1c已通过验收，后续若各自回到原始RTC试验，R5很难直接整合成功经验；这个担忧成立。

## 原流程的缺口

1. “单独验证”和“每次只改一个机制”容易被执行成每次都从B3R-F0.51重新开始。
   这能测单项作用，但没有测该机制在已经改善的模型轨迹上是否仍有增益。
2. 原文把组合集中安排在R5，前面没有要求形成M1→M2→M3的持续版本，导致整合问题发现太晚。
3. 通过范围没有绑定版本。R1c通过的是seed43的Sign-flip/clean，既不应被遗忘，也不能自动宣称LIE/DBA均安全。
4. 把单项效用门失败直接解释为不得研究任何组合，会错过有价值的互补；反过来，单项通过也不证明组合通过。

这些问题不代表原实验白做了：R1c提供有效起点；R2验证了幅度筛选并揭示质量分配变化；
R3旧基线观测可定位累计检测延迟。缺少的是把这些证据接到共同版本上的桥接实验。

## 为什么不能直接把独立收益相加

defenses/rtc/v3.py中，原client cap、谱方向cap与raw cap取最小值后进入同一个QP。
同一上传若被两个模块同时限制，第二个模块未必提供额外权重抑制。
改变accepted weights又会改变accepted anchor的来源与回填，继而改变下一轮模型、上传方向和累计证据。
因此，B0+方向和B0+幅度的效果不能简单加到一起；组合是否互补，必须在真实闭环里比较。
这同时说明R4的anchor安全需要在实际集成cap集合上研究，不能只在B0上证明后照搬。

## 新的版本关系

- B0：B3R-F0.51，固定原始对照。
- D：已通过Sign-flip/clean阶段验收的R1c方向模块。
- N：保留待验证的R2幅度模块；原始批次效用门未通过，历史结论不修改。
- M1=B0+D：在已验证范围内的主线起点；其余条件须转移验收。
- I12候选=M1+N：未接受的交互研究分支，通过新预登记的主线增量与回归门后，才可能成为M2。
- R3候选=M_k+累计改进，R4候选继续继承已接受的M_k；失败只撤回本次新增部分。

如果N未通过I12，M1继续作为后续起点；如果通过，则以后继承M2。
不为了凑齐全部模块而强制纳入N，也不因为N单项效用门未过而永久禁止研究其与D的互补。
一旦主线版本确定，不能按攻击临时打开不同模块、事后选择最好结果，然后称为同一个通用RTC版本。

## 推荐顺序与直接对照

| 阶段 | 主要问题 | 直接对照与继承规则 |
|---|---|---|
| R0/R1 | 方向参考与即时抑制是否有效 | B0与B0+D；已有R1c结果保留 |
| I12/主线桥接 | D的转移表现、D与N是否互补 | 四组B0、B0+D、B0+N、B0+D+N；组合直接与B0+D比较 |
| R3 | 已改善主线是否仍存在慢攻击延迟 | M_k与M_k+累计候选；必要时B0+候选作消融 |
| R4a | 隔离是否真正阻断危险权重 | M_k与M_k+quarantine置零 |
| R4b | 集成cap下的实际anchor是否安全 | 上一已接受主线与增加anchor预算的候选 |
| R5 | 已集成版本能否泛化、各模块贡献是什么 | 固定最终版本、B0、MK/适用挑战者及关键消融；新seed与非IID |

I12四组是一个明确预登记的方向开/关×幅度开/关设计，不是同时盲调多个参数。
N在D开启条件下的增量=(B0+D+N)-(B0+D)；在D关闭条件下的增量=(B0+N)-B0。
两者差异描述交互。ACC、权重、ASR等须分别分析，同seed配对；不把单seed的差值当显著性证明。
后续通常只需M_k和M_k+X的主线配对，加必要消融，不必穷举全部2^模块数的组合。

## 每阶段同时检查两类门

新增机制门：该机制解决的具体问题是否改善，例如Sign-flip抑制、LIE检测延迟、DBA ASR或anchor风险。
主线回归门：此前已验证的clean、Sign-flip、Gaussian以及逐步加入的慢攻击/targeted条件是否保持。
主要终点和容忍界限必须先注册；效用增长不是所有安全模块唯一有意义的目标，但不能追改已返回结果的门槛。

桥接至少覆盖Gaussian/clean/Sign-flip，并补LIE .5方向转移；进入targeted研究前补DBA/scaling回归。
这些条件可以拆成人工批次；拆批只改变执行安排，不缩小已声明的验证范围或提前晋升未通过版本。
Random-v2、LIE .25、Min-Max、Min-Sum、label reversal、新seed和非IID等最终范围仍保留。
身份标签仅作分析；所有候选仍需完整预算检查，不用简单归一化掩盖质量缺失。

## 当前已存在的R3脚本如何处理

核对到3个R3-observe状态文件均completed/exit0/last_round60；完整性、质量门与方向分析尚待本次规划之后验收。
当前脚本中raw_norm_mode和spectral_direction_mode均为observe，代表B0上的诊断，未继承D的实际cap。
它仍有用，但不能把其结果称为M1上的R3证据。此前“不必改脚本”的回答只适用于保留这批只读诊断。

已经执行的脚本、manifest和原始日志保持不变；不得把配置改成cap后沿用旧run_id或重新标注为集成实验。
下一步先验收这些产物，随后准备独立目录、独立冻结的I12/主线转移实验。
在缺少主线转移证据时，不继续把新的R3算法只加到B0上；必要的M1方向观测可纳入桥接批次。
旧结果是否可复用，仍逐配置、代码、数据、攻击、随机流严格核验，不因名称相似默认复用。
